# 2026-10-29 — Recette design, API : retirer un groupe que le bot a quitté (REG-28) — done
Recommandation acceptée par Charles le 29/10 00h22 :
- REG-28 : « Faut-il pouvoir retirer depuis le CRM un groupe que le bot a quitté, avec une nouvelle route API ? Je recommande oui, seulement pour les groupes quittés ou interdits : sinon la liste s’encrasse et l’ambre ne s’éteint jamais. »
Fait :
- Serveur. `DELETE /v1/settings/telegram/chats/:id` (propriétaire, sans redemande du mot de passe : aucun jeton n’est touché) retire un groupe dont le bot est sorti (`left`) ou a été exclu (`kicked`), et seulement ceux-là (`mayRemoveChat`, domaine pur). La lecture de l’appartenance, sous verrou de ligne, et la suppression sont dans la même transaction : un bot revenu entre-temps garde son groupe (409 `telegram_chat_member_conflict`, constante dans les contrats). La suppression emporte les routes du groupe (cascade) et garde ses envois (voir Relecture), fait avancer la version du routage pour que les écrans ouverts rechargent, et écrit `telegram_chat.remove` dans `audit_log`. 404 pour un groupe inconnu.
- `GET /v1/settings/telegram` montre désormais aussi ces groupes (`membership` `left` ou `kicked`) : jusqu’ici ils disparaissaient de la liste alors que leurs routes « cassées » restaient (ADR 0020 § 8 dit « le groupe passe retiré »), donc rien à retirer n’était visible.
- Écran. Réglages › Telegram › Bots et groupes : sous les groupes d’un bot, chaque groupe quitté ou interdit dit pourquoi (« Supergroupe · le bot a été exclu de ce groupe », « Groupe · le bot n’est plus dans ce groupe ») et propose « Retirer de la liste », avec une confirmation dans la page (« Ses routes partent avec lui. Si tu rajoutes le bot à ce groupe, il revient tout seul. »). Ces groupes ne sont plus proposés au routage ni comptés comme nouveaux pendant l’attente d’un groupe.
Pas fait : un groupe où le bot est encore mais sans droit d’écrire (cité dans le constat) reste dans la liste, comme la recommandation le demande : lui rendre ce droit est la sortie.
Relecture (Telegram, Bilan, Extension) :
- Les envois d'un groupe retiré ne partent plus avec lui : le décompte de la nuit du Dashboard (`countTopics`) les lit, et un groupe retiré le matin aurait effacé les urgences de la nuit. Migration 0037 : `telegram_deliveries.chat_id` devient nullable, avec une clé étrangère `ON DELETE SET NULL` supprimée puis recréée ; `chat_title` est rempli depuis `telegram_chats` pour les lignes existantes, puis passe en NOT NULL, et chaque nouvel envoi l'écrit. Dans la transaction du retrait, ce qui attendait passe en échec et ce qui était en cours d'envoi passe en `unknown`, les deux avec le nouveau motif `chat_removed` (« Le groupe a été retiré de la liste avant l'envoi : ce message n'est pas parti. »). Un groupe retiré n'est jamais destinataire : `threadRoots` l'ignore et `parentState` ne le compare pas. L'unicité (source, groupe) garde le NULLS DISTINCT, ce qui est voulu et écrit dans le schéma et le README.
- `TELEGRAM_CHAT_MEMBER_CONFLICT` est placé après le type `TelegramMembership`.
- Écran : un bot exclu de son seul groupe renvoie vers Bots et groupes, au lieu de « Choisis au moins un groupe ». Un groupe à retirer met le bandeau en ambre. Le retrait affiche « Retrait… » et ne prend pas de second clic. La feuille « Ajouter à un groupe » ne compte comme déjà connus que les groupes où le bot est encore (`knownChatIds`) : un groupe rajouté est retrouvé.
Migration : 0037 (numéro attribué par Bilan).
Décisions : pas de redemande du mot de passe (la règle ADR 0016 vise les jetons) ; un 404 côté écran vaut retiré (même fin).
Découvertes : aucune (la cascade sur les envois, relevée à la première tête, est corrigée dans cette PR).
Candidats à suppression : aucun.
