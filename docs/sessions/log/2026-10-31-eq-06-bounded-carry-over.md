# 2026-10-31 — ADR 0038 : le report borné dans le moteur de paie (fil Équipe) — in_progress
Fait :
- Contrats : `CARRY_OVER_RANK_MAX` (2) et `CarryOver.rank` (1 par défaut : un relevé compté avant le rang lit un premier report ; un report négatif toujours au rang 1) ; `positiveCarryRankIn` et `carryOverRank`, purs, lus par le moteur, la validation et l'écran ; `DEFAULT_INVOICE_DUE_DAYS` passe de 15 à 60, le réglage `due_days` accepte de 45 à 60 (`INVOICE_DUE_MIN_DAYS`).
- Moteur (`nirvana-2`) : un total positif sous le minimum n'est reporté que si le report positif qui entre est au rang 1 au plus ; au rang 2, le relevé verse, même sous le minimum. Une quinzaine négative garde le rang tant que le cumul reste positif ; un cumul nul ou négatif le remet à 1. Le relevé final verse tout, comme avant.
- Validation : le report sortant s'écrit avec son rang (`carryOverRank`).
- Migration 0043 (réservée par Bilan) : `carry_overs.rank` (1 par défaut), le CHECK qui refuse un rang 3 et un report négatif au rang 2, `keep_carry_over` qui veut le rang du report d'avant plus un quand les deux sont positifs, 1 sinon ; `billing_settings_delays_check` entre 45 et 60 (aucune ligne n'existe). Le report repris d'Imperium (rang 2) attend la migration de l'import, noté dans la fiche EQ-07.
- Écran (Paie, Commissions) : le deuxième report de suite le dit (« la quinzaine suivante le verse, même sous le minimum »), et un relevé qui verse sous le minimum après deux reports dit pourquoi ; sans cette phrase, un versement sous le minimum se lirait comme une erreur.
- Tests : unitaires du moteur (9 €, 4 €, 1 € : deux reports puis 14 € versés ; −5 € après 9 € garde le rang 2 ; cumul négatif qui remet à 1), propriétés (jamais versé sous le minimum hors relevé final ou montant reporté deux fois ; rang jamais au-delà de 2), contrats (rang, délais), écran (quatre phrases) ; intégration : une vraie validation écrit le rang 2 et la quinzaine suivante verse les 8 € de Léa (`payroll-validation`), la base refuse un rang faux, un troisième report et un négatif au rang 2 (`payroll-rls`, les deux scénarios de Bilan), délais 45 et 60 (`invoices-rls`, `payroll-invoices`).
- Glossaire (« Report », « Minimum de versement », nouveau « Rang du report »), fiches EQ-06 et EQ-07, `README.md` du module, `data-model.md`.
Pas fait : les alertes d'échéance (ambre à J-7, rouge dépassée), au lot 8 d'EQ-06.
Décisions : aucune date d'entrée en service dans le code. Un report écrit avant la règle lit le rang 1 ; le premier relevé dont le montant change est donc celui qui reçoit un report au rang 2, écrit à la validation d'une quinzaine après la mise en service : sa propre quinzaine n'avait pas commencé à ce moment-là, comme l'ADR le veut, et aucun relevé validé n'est recalculé.
Découvertes : le déclencheur `keep_carry_over` et `commission_statements_engine_check` refusent un relevé et un report d'Imperium (moteur `imperium`, pas de relevé validé de Nirvana) : la migration de l'import (EQ-07) devra les adapter.
Candidats à suppression : aucun.
